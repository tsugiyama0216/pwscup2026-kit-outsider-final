## 初回指摘と修正確認

**P1：予約が可動な出力フォルダ内だけにあり、出力移動後の再測定を防げない。**

確認時点の `reserve_and_measure()` は `release/reservation.json` に予約を書き、
別の `release_ledger/` には実行中の `active.lock` だけを作る。ロックは終了時に
削除される。出力 `release/` を別名に移動した後で同じ runner を実行すると、
予約なしと判定され、同じ予算表示で producer をもう一度呼べる。

公開のダミー producer と一時フォルダだけで再現した結果、
「予約・生成 → 出力フォルダを別名へ移動 → 同じ場所で再開」により producer が
**2 回**呼ばれた。期待される回数は 1 回。私的入力や本番出力は使用していない。

修正案：可動な出力から独立した固定台帳に、producer より先に永続予約を保存する。
予約は出力・入力・設定・ソースの固定識別子に結び付け、台帳に予約があるのに
出力モデルがない場合は再測定を拒否する。出力移動・削除後の再開と、異なるパスへ
コピーした出力の利用を検査する回帰テストを追加する。台帳を手動削除すれば予算が
戻る、という扱いにしてはならない。

**P2：完全一致を主張する保存検証が既定の浮動小数点許容差を使っている。**

`assert_preservation()` は `pd.testing.assert_frame_equal()` を既定値で呼ぶ。
浮動小数点列では小さな差を許容するため、manifest の
`predictor_rows_preserved_exactly` と検証条件が完全には一致しない。
予測変数表・各 rare 層の outcome triple の双方に `check_exact=True` を付ける。
現行 optimizer が列を変更したという指摘ではなく、検証条件の厳密さの問題である。

**P2：完了済み出力の再開時に manifest の会計・freeze 識別子も検証すべき。**

現行再開経路は manifest 内の C/model ハッシュを照合するが、manifest の
`freeze_sha256`、会計、`public_n`、`base_C_sha256` と固定記録との一致は明示的に
検証しない。古い／取り違えたメタデータを拒否するチェックを追加するとよい。

上記を担当者に通知した後、次の修正をコードとテストで再確認した。

- `reserve_and_measure(..., ledger_dir=...)` は、出力とは別の固定
  `release_ledger/reservation.json` を排他的作成・fsync し、その後に出力側の
  予約コピー、最後に producer の順で実行する。再開時は二つの予約の一致と
  完了済みモデルを検査し、出力が移動・消失しても新規測定を許可しない。
- 出力移動後・別出力先で同じ台帳を使う場合の拒否テストが追加され、
  通常再開・失敗後の拒否・freeze/モデル破損の拒否と合わせて **5 テスト成功**。
- 予測変数と rare 層別 outcome triple の保存検証に `check_exact=True` が追加された。
- 完了済み manifest 再開時に会計、人数、freeze ハッシュ、base C ハッシュを
  固定記録と照合するチェックが追加された。

再レビューした runner の SHA-256：
`c77f57576057f9d6f17799e45ed2ed88a6b662a8a69f7c52675ac81e2084cfdd`

台帳自体の故意の消去や、記録を除外した別管理領域での再測定までを防ぐ
暗号学的な集中会計ではない。固定台帳を保存する運用契約が前提となる。

## 確認できた適切な点

- B の読み込みは producer 内だけにあり、固定台帳の予約と出力側の予約を
  排他的作成・flush・fsync した後でのみ producer が呼ばれる。同じ予約の再開では、
  完了済み DP モデルを再利用し、測定失敗・不完全モデルは再試行を拒否する。
- freeze の一致、予約と完了記録の freeze ハッシュ、保存モデルのハッシュを
  確認する。固定記録に入力・出力の絶対パスが含まれ、既存 freeze を保持したまま
  異なる場所で使う場合は一致しない。
- 公開選択 JSON の完了状態・ハッシュ、採用予算、公開設定、コードハッシュを
  確認する。採用基準は公開試験 6 件で平均 Cox >=0.95、最小 Cox >=0.92 を
  最初に満たす予算。設定・会計も公開人数 1049、δ0、過去 ε14 と照合する。
- B/B_self/utility_ref のハッシュを作らず、公開 A_bg/schema のみをハッシュ照合する。
  固定済み joint14 の C/model ハッシュも確認する。
- B と公開範囲で前処理した表は producer のメモリ内にのみ存在する。保存する
  モデルは公開 target と noisy integer を含む DP target、および公開会計であり、
  raw Cox β/SE、私的 clip norm、成功・失敗フラグを保存する経路はない。
- 最適化は保存済み DP target と合成 C のみを用いる。私的評価コードの import や
  私的スコアによる採用判断は runner にない。新規予算を ε とすると、全体の
  表示は **14+ε、δ0** であり、再利用だけの実行で追加支出を発生させる必要はない。
- C 作成中に停止した場合は、完了済み DP モデルから固定 seed で後処理を
  再実行できる設計であり、ここに再測定は必要ない。

レビュー時点で公開予算試験は進行中だったため、採用予算の最終数値や試験結果を
このレビューで確定してはいない。
